군수실 일정 관리 — 개발자용 배포·업데이트 안내
작성 기준: 2026-10-02 / 준비된 버전: v2.1.1

현재 상태

GitHub 저장소는 dpqksr5501/schedule-doc-system이며 공개 저장소입니다.
조회 시점의 최신 정식 배포는 v1.0.1입니다.
v2.1.0 소스와 태그를 먼저 push했으며, GitHub 경로 검사 수정은 v2.1.1에 포함합니다.
정식 공개 전 검토용 초안을 준비하는 단계입니다.

권장 배포 순서: 소스 반영 → 버전 태그 → 자동 빌드 → 초안 검토 → 공개

1. 변경한 소스를 GitHub에 반영합니다.

VS Code 또는 GitHub Desktop에서 변경 파일을 검토하고 커밋한 뒤 main에 올립니다.
현재 작업에서는 원래 일회성 스크립트를 tools/legacy로 옮긴 변경도 포함됩니다.
로그, 일정 백업, 실제 업무 데이터는 소스나 릴리즈 첨부에 추가하지 마세요.
dist와 release는 빌드 산출물이므로 일반 소스 커밋에 넣지 않습니다.
로고 PNG 두 개는 .gitignore 예외에 포함되어 소스와 함께 커밋할 수 있습니다.

2. 버전 번호와 태그를 맞춥니다.

앱 버전은 app_info.py의 VERSION 한 곳에서 관리합니다.
현재 VERSION은 2.1.1이므로 태그는 정확히 v2.1.1이어야 합니다.
소스를 커밋하고 main에 올린 다음 PowerShell에서 실행합니다.

  git tag v2.1.1
  git push origin v2.1.1

이 명령은 공개 GitHub의 버전 태그를 만드는 작업입니다.
이미 배포한 태그는 덮어쓰지 말고 다음 버전 번호를 사용하세요.

3. GitHub Actions가 배포 파일을 만듭니다.

.github/workflows/windows-release.yml이 동작합니다.
고정 의존성 설치 → 자동 검사 → EXE 빌드 → EXE 자체 검사 → WebView2 검사를 수행합니다.
태그와 VERSION이 다르거나 검사에 실패하면 배포 초안을 만들지 않습니다.
소스가 main에 올라간 것만으로는 정식 릴리즈가 공개되지 않습니다.
GitHub 저장소의 Actions 탭에서 해당 태그의 실행 결과를 확인하세요.

4. Releases에서 초안을 검토하고 공개합니다.

태그 빌드가 통과하면 Draft(초안) 릴리즈가 준비됩니다.
초안에는 아래 파일이 첨부됩니다.

  GunsuSchedule.exe                         앱 내 업데이트가 받는 파일
  GunsuSchedule-v2.1.1-Windows.zip           처음 설치하는 분에게 전달할 묶음
  SHA256SUMS.txt                            실행 파일 해시
  release-manifest.json                     버전·이름·크기·해시

ZIP 안에는 실행 파일, 사용설명서.txt, 처음사용_5분안내.html이 들어 있습니다.
릴리즈 설명은 docs/releases/v2.1.1.txt에서 가져옵니다.
설명과 첨부 파일을 확인하고, Pre-release를 선택하지 않은 정식 버전으로 공개하세요.
새 정식 버전을 최신 릴리즈(Latest)로 지정했는지도 확인합니다.
GitHub는 초안의 첨부 파일을 준비한 후 공개할 수 있습니다.

5. 공개 후 업데이트 연결을 확인합니다.

공개 릴리즈 API 주소:
https://api.github.com/repos/dpqksr5501/schedule-doc-system/releases/latest

tag_name이 새 태그인지, 이름이 GunsuSchedule.exe인 첨부 파일이 있는지 확인합니다.
그 파일의 digest가 sha256:... 형식이어야 합니다.
예전 v1.0.1 첨부 파일은 schedule-doc-system.exe라는 이름이지만,
새 버전부터는 반드시 GunsuSchedule.exe라는 고정 이름을 사용합니다.
ZIP만 올리거나 실행 파일 이름을 바꾸면 새 앱의 업데이트 실행은 되지 않습니다.

v2.1.1 앱에서 v2.1.1은 이미 같은 버전이므로 새 업데이트로 표시하지 않습니다.
실제 앱 간 갱신 검증에는 다음 정식 버전(v2.1.2 등)이 필요합니다.
시험을 위해 가짜 새 버전 번호나 예전 실행 파일을 올리지 마세요.
현재 자동 검사에는 네트워크 실패·잘못된 해시·다운로드 오류·시작 실패의 방어가 포함됩니다.
실제 정식 GitHub 릴리즈를 받아 재시작하는 운영 검증은 공개 후 별도로 확인해야 합니다.

아버님 PC의 업데이트 방법

  백업 · 복원 · 업데이트
    → 지금 백업하기
    → 새 버전 확인
    → 새 버전 내용 확인
    → 다운로드 후 재시작

다운로드한 EXE의 출처·크기·SHA-256을 확인한 뒤 새 버전 폴더에 저장합니다.
새 화면과 일정 데이터가 정상적으로 준비되면 바로가기를 새 버전으로 전환합니다.
기존 실행 파일은 복구용으로 보관합니다. 실패하면 안내하고 기존 버전 재실행을 시도합니다.
자동 다운그레이드로 새 형식의 일정 데이터를 덮어쓰지는 않습니다.
일정 확인 없이 자동으로 프로그램을 닫고 업데이트하지 않습니다.

첫 v1.0.1 → v2.1.1 전환은 기존 일정 백업 후 새 ZIP을 직접 실행하는 방법을 권장합니다.
구버전의 임시 브라우저 저장소는 실행 경로가 바뀌면 보이지 않을 수 있습니다.
일정이 비어 있으면 백업 파일 선택으로 기존 JSON 자료를 가져오세요.
전체 복원은 현재 내용을 바꾸므로 건수와 기간을 확인하세요.

다음 버전 배포

  ① 변경·검사 완료
  ② app_info.py VERSION을 2.1.2 등 새 번호로 변경
  ③ docs/releases/v2.1.2.txt에 사용자에게 보여 줄 변경 설명 작성
  ④ 필요한 설명서의 버전 안내도 갱신
  ⑤ 커밋·main 반영 후 git tag v2.1.2 / git push origin v2.1.2
  ⑥ Actions 통과와 초안 첨부 검토 후 정식 공개

정식 버전은 X.Y.Z 형식입니다. beta·rc 등 사전 배포는 일반 앱에서 자동 적용하지 않습니다.
태그와 코드 버전이 같아야 하며, 이미 공개한 버전의 EXE를 새 빌드로 덮어쓰지 않습니다.

인터넷·기관 환경

현재 업데이트는 공개 GitHub 저장소를 로그인 없이 조회하는 방식입니다.
저장소가 비공개로 바뀌면 별도의 배포 인증 구조가 필요합니다.
기관망에서 GitHub 접근이 제한되면 전산 담당자가 허용한 경로로 새 ZIP을 전달하세요.
업데이트 확인이 실패해도 기존 앱의 일정 입력과 로컬 문서 작업은 계속 사용할 수 있습니다.
HWP 출력은 별도로 한글 설치와 자동화 사용이 가능한 환경이어야 합니다.
